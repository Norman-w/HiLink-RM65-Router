# 架构：RM68 轻转发 + MacBook 旁路分析（按 MAC 匹配）

> 目标：平时 RM68 当正常家用路由；仅对指定 MAC（手机/平板/电子相册/电视等）在 Mac 在线时把流量旁路到 macOS 做检测/过滤；Mac 离线则 **fail-open 放行**。  
> 结论：**方向正确，能避免把重度分析压垮 RM68**；但要实现「广告/非法请求过滤 + 视频设备不卡」，必须分层，不能把所有包无脑全量 MITM。

---

## 1. 你的想法对不对？

**对，而且这正是「控制面轻、分析面重」的正确拆分。**

| 角色 | 职责 | 负载 |
|------|------|------|
| RM68 / OpenWrt | 正常路由 + **按 MAC 打标/分流** + 健康检查 + fail-open | 轻（规则匹配 + 转发） |
| MacBook（有线挂 LAN） | DPI / 广告域名 / 非法 URL / 调试抓包 / 策略决策 | 重 |
| 未匹配 MAC 的设备 | 走 RM68 默认转发，完全不经 Mac | 零额外开销 |

这样：

- RM68 **不会**被 Suricata/机器学习/完整 HTTPS 解密拖垮。  
- 平时无匹配、或 Mac 离线 → 就是普通路由器。  
- 调试特定设备时再「挂上分析器」。

---

## 2. 推荐数据路径（不要做成「包到用户态再回送」）

错误直觉：每个包在 OpenWrt 用户态读出来 → TCP 发给 Mac → Mac 再发回来。  
这会把 RM68 **用户态拷贝**打满，视频流量很容易卡。

正确做法：**内核策略路由 / 透明代理，Mac 做 middlebox**。

```
                    ┌─ Mac 离线 / 心跳失败 ─┐
客户端(指定MAC) ──► RM68 ──┤                      ├─► 直连 WAN（fail-open）
                    └─ Mac 在线 ────────────┘
                              │
                              ▼
                     有线到 MacBook
                     (透明代理 / 网关旁路)
                              │
                     分析：放行 / 阻断 / 改 DNS
                              │
                              ▼
                            WAN
```

### 2.1 两种模式（建议都做）

**模式 A — 旁路观测（调试首选，几乎不拖垮）**

- OpenWrt：`tee`/`nflog`/端口镜像，把匹配 MAC 的包 **复制一份** 给 Mac。  
- 主路径仍直接出 WAN，**零回程**。  
- 适合：看电子相册/电视到底请求了哪些广告域名、非法 CDN、诡异 UDP。  
- 不能主动拦截（只看不拦）。

**模式 B — 串接过滤（要拦广告/非法请求）**

- OpenWrt：对匹配 MAC 做 **policy routing** 或 **透明代理 REDIRECT/TPROXY**，下一跳指向 Mac。  
- Mac 跑：`mitmproxy` / `Clash`/`sing-box` / `Squid` + 规则库，或自研分析服务。  
- 决策后从 Mac 再出网（Mac 需双接口或策略 NAT），或回 RM68 指定出口。  
- Mac 心跳失败 → RM68 **立刻撤规则**，流量直通。

日常建议：**默认 A；需要过滤时对少量设备开 B。**  
视频大流量设备优先 DNS/SNI 级拦截，避免全量解密。

---

## 3. 「外接件装在 MacBook」怎么理解

MacBook 侧需要的是 **稳定、低延迟的有线旁路口**，不是让 Mac 当 Wi‑Fi AP。

| 外接形态 | 说明 |
|----------|------|
| USB‑C / Thunderbolt 千兆或 2.5G 网卡 | 最实用；插 RM68 的 LAN |
| 扩展坞双网口 | 一口进（来自 RM68 分流）、一口出（可选独立上行） |
| 纯 Wi‑Fi 连 RM68 | **不推荐**做串接主路径（抖动大、易环路、睡眠断链） |

OpenWrt 侧小软件只做三件事：

1. **设备集合**：监视 MAC 列表（可 Web/UCI 配置）。  
2. **Mac 存活探测**：对 Mac 的旁路 IP 做 TCP/HTTP 心跳（如每 2s）。  
3. **装/卸规则**：在线则挂 nftables/pbr；离线则清空（fail-open）。

不必在 RM68 上做深度解析。

---

## 4. 会不会拖垮 RM68？

| 场景 | RM68 压力 | 说明 |
|------|-----------|------|
| 无匹配设备 / Mac 离线 | ≈ 普通路由 | 理想态 |
| 仅 DNS/域名规则过滤 | 很低 | `dnsmasq`/`nft set` 拦截广告域 |
| 匹配 MAC + 内核策略路由到 Mac | **中低** | 转发在内核，可接受 |
| 匹配 MAC + OpenWrt 用户态逐包转发 | **高，易拖垮** | 避免 |
| 全屋设备全量 HTTPS MITM | 高（在 Mac）且设备难装证书 | 不适合电子相册/电视 |

视频设备（4K 拉流）若走模式 B 全流量串接：瓶颈在 **Mac 代理吞吐与延迟**，不是 RM68 CPU——Mac 睡着或 USB 网卡不稳会卡播，所以 **fail-open 必须快（秒级）**。

---

## 5. 广告 / 非法请求：能滤到什么程度？

| 手段 | 对手机/平板 | 对电子相册/电视 | 要不要 MITM |
|------|-------------|-----------------|-------------|
| DNS 黑洞（广告域名列表） | 很好 | **很好（首选）** | 否 |
| 阻断已知广告 IP / CDN | 好 | 好 | 否 |
| TLS SNI / HTTPS 明文 ClientHello 域名 | 较好 | 较好 | 否 |
| 完整 HTTPS 解密 | 需装 CA；App 可能证书固定 | **多数装不了 CA** | 是 |
| QUIC/HTTP3 | 需阻断 UDP/443 迫降 TCP 或放行 | 同上 | 复杂 |

**现实路径（推荐落地顺序）：**

1. **DNS 过滤 + 域名/SNI 黑名单**（解决 80% 广告与追踪）。  
2. 调试期用模式 A 抓包，把「电子相册真实请求」沉淀成规则。  
3. 仅对「你能装信任证书的手机/平板」开 HTTPS MITM。  
4. 电视/相册：**不要**指望完整解密；用 DNS/IP/SNI + 偶发抓包分析。

「非法请求」若指木马回连/异常域名：旁路观测 + 威胁情报域名列表即可；若指内容审查级 DPI，成本陡增且对加密流量仍受限。

## 6. Fail-open 逻辑（必须做成状态机）

```
状态: IDLE（直通） / ACTIVE（分流到 Mac） / DEGRADED（探测失败宽限）

心跳 OK 且 存在匹配 MAC 会话需求 → ACTIVE
心跳 N 次失败（如 3×2s）→ DEGRADED → 立即卸规则 → IDLE（全部放行）
心跳恢复 → 再挂规则（可延迟 5s 防抖）
```

注意：

- 卸规则要用 **原子替换 nft set / 整链 flush**，避免半中间状态把连接打坏。  
- 正在播放的长连接：从 ACTIVE→IDLE 可能闪断一次，可接受；比「Mac 挂了全家断网」好。  
- MacBook 合盖睡眠 = 离线，必须 fail-open（或外接电源 + 防睡眠策略）。

---

## 7. 和「平时当正常路由」是否冲突？

**不冲突。** 条件：

1. 默认策略：无 MAC 命中 → 零旁路规则。  
2. 旁路口只服务「分析 VLAN 或专用网段」，避免 Mac 被别的设备当网关误用。  
3. 非目标设备 DHCP 正常、Wi‑Fi 体验与现在评估报告一致（AX3000 家用档）。  
4. 分析软件崩溃不影响路由（心跳失败即直通）。

## 8. 推荐实现栈（务实）

### OpenWrt（RM68）

- `nftables`：`ether saddr` 匹配 MAC set。  
- `pbr` 或自写小脚本：把命中流量指到 `macbook` 接口/网关。  
- 可选：DNS 级 `nft set` 广告域（不经 Mac 也能拦）。  
- 自研 `hlk-divertd`：心跳 + 装卸载规则（几十 KB 级，别搞重框架）。

### macOS

- 有线网卡固定 IP，如 `192.168.1.2`。  
- 分析服务监听透明代理端口（或作为该网段网关）。  
- 规则引擎：广告 host 列表 + 自建「设备指纹 → 允许域名」。  
- 调试 UI：按设备看请求时间线（电子相册特别有用）。

### 外接件

- 第一版：成品 USB‑C 网卡即可验证架构。  
- 以后再做成「专用旁路盒」（双网口小配件），逻辑不变。

## 9. 路径是否正确？一句话

**正确：RM68 只做「认 MAC + 健康检查 + 内核分流/直通」，MacBook 做检测分析与过滤决策；离线放行。**  

要补上的关键修正：

1. 用 **内核分流**，不要用户态逐包转发。  
2. 过滤以 **DNS/SNI/IP 名单** 为主，全量 HTTPS MITM 只对可控设备。  
3. 视频/相册调试先用 **旁路镜像（模式 A）**，再对需要拦截的开串接（模式 B）。  
4. Fail-open 做成秒级状态机，Mac 睡眠不得导致断网。

这样平时就是正常路由器；插上 MacBook 外接网卡并打开分析软件时，才对指定设备进入「监控/过滤模式」。

## 10. 「分流在内核」要不要改 OpenWrt / 自研内核？

### 一句话

**默认不需要改内核，也不需要「先装自研内核再装 OpenWrt」。**  
OpenWrt = 内核 + rootfs 的完整系统；分流用的是系统里**已有的** netfilter / 路由子系统，你只要装软件包、写配置/小守护进程。

### 三层分别做什么

```
┌─────────────────────────────────────────────┐
│  你开发的：hlk-divertd / LuCI / 配置脚本      │  ← 用户态（心跳、装卸载规则）
├─────────────────────────────────────────────┤
│  OpenWrt 软件包：firewall4, pbr, dnsmasq…   │  ← 仍用户态，调用内核接口
├─────────────────────────────────────────────┤
│  Linux 内核（随 OpenWrt 一起烧录）            │  ← 真正转发包（nft / ip rule）
└─────────────────────────────────────────────┘
```

| 做法 | 要不要重编内核 | 要不要重烧整机 | 适用 |
|------|----------------|----------------|------|
| UCI/`nft`/ `pbr` 配规则 + 自写用户态守护进程 | **否** | 通常 **否**（opkg/自定义 ipk 即可） | **本方案首选** |
| 启用某个未打开的内核选项（极少见） | 要编 OpenWrt 内核 | 要刷含新内核的固件 | 缺 `TPROXY` 等配置时 |
| 自写 `.ko` 内核模块 | 针对该内核编译模块 | 可只装 ko，或打进固件 | 现有 nft/路由不够用时（本需求基本不需要） |
| 完全自研内核，再「旁边」装 OpenWrt | — | — | **不可行/无意义**：不能当两个互不影响的系统叠着装 |

### 和「两个互不影响」的关系

- **不是**两套 OS 并排：不能先刷一个裸内核，再刷一个不影响它的 OpenWrt。  
- **是**一层：厂商或你编译的 **OpenWrt 固件**里已经带好内核；你的分流逻辑是 **OpenWrt 之上的应用**，和 Wi‑Fi/路由共存，平时不开规则就等于普通路由。  
- MacBook 侧软件与 RM68 **完全独立**；只有 LAN 上的 IP/心跳和分流下一跳有关系。

### 推荐落地顺序

1. 用海凌科提供的 OpenWrt 能开机、当路由。  
2. 确认带 `nftables`（firewall4）和策略路由；缺什么用 `opkg` 或编一个 **只含软件包的自定义固件**（多数情况仍不用改内核源码）。  
3. 开发用户态 `hlk-divertd`：探测 Mac → `nft add/flush` 或调 `pbr`。  
4. 只有实测发现内核缺特性时，再在 OpenWrt 构建系统里改 `kernel_menuconfig` 重新出固件——那是例外，不是起点。
